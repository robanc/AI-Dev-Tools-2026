# TaskLane — Product Specification

**TaskLane** is a small full-stack Kanban application for an individual to track tasks across **To Do**, **In Progress**, and **Done**. It runs locally and stores tasks in SQLite so they survive page refreshes and application restarts.

Status: Approved. Implementation will be added in later homework steps.

## 1. Target users

Students and individual developers who want a simple way to track tasks for a small project.

The homework version provides one shared board without accounts or login. It assumes one person uses the application.

## 2. Core user stories

- As a user, I can create a task with a title and optional description.
- As a user, I can see tasks grouped by status to understand my progress.
- As a user, I can view and edit a task’s full details.
- As a user, I can move a task between columns using a status control.
- As a user, I can delete a task I no longer need.
- As a user, I can return after refreshing or restarting the application and find my saved tasks.

## 3. Functional requirements

### Board

- Display three fixed columns: **To Do**, **In Progress**, and **Done**.
- Load saved tasks from the backend when the board opens.
- Display each task’s title and an optional description preview.
- Provide an empty state for columns without tasks.
- Order tasks by creation time, newest first within each column. Manual ordering is not supported.

### Task creation and editing

- Provide an **Add task** action.
- Require a title containing at least one non-whitespace character.
- Trim surrounding whitespace from titles and limit them to 200 characters.
- Allow an optional plain-text description of up to 2,000 characters.
- Create new tasks in **To Do**.
- Allow users to open a task to view its full description and edit its title or description.
- Allow users to cancel an edit without saving changes.
- Show validation errors near the relevant fields.

### Status changes

- Provide a status dropdown on each task card.
- Allow movement directly between any of the three statuses.
- Save the change through the backend and update the board after success.
- Preserve the task’s title and description when its status changes.

### Deletion

- Ask for confirmation before deleting a task.
- Remove the task from the board and database after confirmation and a successful backend response.
- Canceling the confirmation leaves the task unchanged.
- Deletion is permanent; there is no undo or archive.

### Persistence and errors

- Use a backend API for all task reads and changes.
- Store tasks in a file-based SQLite database.
- Validate task input in both the frontend and backend.
- Show loading feedback while fetching the board.
- Show a clear error if loading or saving fails.
- Preserve entered form values when a save fails and allow retrying.
- Prevent duplicate form submissions while a request is pending.

## 4. Main screens

| Screen or interface | Contents |
|---|---|
| **Board — main page** | TaskLane name, Add task button, three status columns, task cards, loading and error feedback |
| **Task form — modal dialog** | Create or view/edit a task, title and description fields, Save and Cancel buttons |
| **Delete confirmation — dialog** | Task identification, Delete and Cancel actions |

No separate dashboard, settings page, or account screens are required. The board should be usable on desktop and narrow screens, with columns stacking vertically when necessary. Controls should have clear labels and support keyboard use.

## 5. Main data and entities

Only one stored entity is needed: **Task**.

| Field | Type | Rules |
|---|---|---|
| `id` | Integer | Unique identifier generated by the database |
| `title` | String | Required, trimmed, 1–200 characters |
| `description` | Text | Optional, maximum 2,000 characters; defaults to empty text |
| `status` | String | One of `todo`, `in_progress`, or `done`; defaults to `todo` |

The board and columns are fixed application structure, so they do not need database tables. Creation order can use the generated task IDs.

### Backend API

| Method and path | Purpose |
|---|---|
| `GET /api/tasks` | List all tasks |
| `POST /api/tasks` | Create a task |
| `PATCH /api/tasks/{id}` | Update title, description, or status |
| `DELETE /api/tasks/{id}` | Delete a task |

The list response includes full task details, so a separate detail endpoint is unnecessary. Invalid input returns a validation error; updates or deletions targeting a missing task return a not-found response.

## 6. Acceptance criteria

1. **Empty board:** Given an empty database, opening TaskLane shows all three columns and an Add task action.
2. **Create:** Saving a valid title creates exactly one task in To Do. An optional description is saved with it.
3. **Validate:** Empty or whitespace-only titles, over-limit text, and unsupported statuses are rejected without changing stored data.
4. **View and edit:** Opening a task shows its full details. Saving valid edits updates the board and database; canceling leaves the task unchanged.
5. **Move:** Selecting another status moves the task into the corresponding column and persists the change.
6. **Delete:** Confirming deletion removes the task permanently. Canceling leaves it intact.
7. **Persist:** Created tasks, edits, and status changes remain after a browser refresh and backend restart using the same database file. Deleted tasks do not return.
8. **Handle errors:** A failed API request shows useful feedback without falsely presenting the operation as successful. Failed form saves retain entered values.
9. **Use the interface:** Main actions work with a keyboard, and all columns and controls remain accessible at narrow viewport widths.
10. **Run locally:** Documented setup and start commands launch the frontend and backend without requiring a hosted service.

### Required tests

- **Backend:** Use an isolated test database to test creation, listing, editing, status changes, deletion, validation, and missing-task responses.
- **Frontend:** Test board rendering, task creation and validation, editing and cancellation, status changes, delete confirmation, and visible API error handling.
- **Integration verification:** Verify the connected frontend and backend complete the main task lifecycle and preserve data across refresh and restart.

## 7. Non-goals / out of scope

- Accounts, authentication, and user profiles
- Team collaboration, sharing, and real-time synchronization
- Multiple boards or configurable columns
- Drag-and-drop and manual task ordering
- Due dates, priorities, labels, and assignees
- Search, filters, and sorting controls
- Comments, attachments, subtasks, and rich-text editing
- Notifications, activity history, archives, and undo
- Cloud deployment, offline mode, and external integrations

## 8. Assumptions and constraints

- **Name:** TaskLane.
- **Frontend:** A browser application using Node.js for development tooling. Proposed default: React with Vite and JavaScript.
- **Backend:** Python with FastAPI; dependencies and execution managed with `uv`.
- **Database access:** SQLAlchemy.
- **Final database:** File-based SQLite.
- **Execution:** Local frontend and backend processes; no deployment requirement.
- **Testing:** Proposed defaults are pytest for the backend and Vitest with React Testing Library for the frontend.
- **Scope:** One board and one intended user. Anyone able to reach the running application can access that board.
- **Storage:** Persistence assumes the SQLite file remains in place. Backups and recovery are outside scope.
- **Initial state:** A fresh installation starts with an empty board.
- **Implementation priority:** Complete, tested task management with a simple readable interface.
